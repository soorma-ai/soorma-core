## 2. Images (Q2 A)

- **Build stage**: `node:26.13.0` (pinned by digest). Installs with the frozen lockfile,
  compiles each NestJS package through its `tsconfig.build.json` (T-OI-09), and runs
  `pnpm deploy --prod` for `services/org-gateway`
- **Run stage**: `gcr.io/distroless/nodejs26-debian13:nonroot` (pinned by digest). Only the
  compiled output and production dependencies are copied in. **No shell, no package
  manager**; user `nonroot` (65532)
- **Entry points**: `node dist/main.js` (S1), `node dist/migrate.js` (`org-migrate`),
  `node dist/healthcheck.js` (the Compose healthcheck: distroless has no shell or curl)
- **`.dockerignore`** excludes `deploy/local/.secrets/`, `.git`, and `node_modules`. The
  Dockerfile **copies explicit paths only**, never the whole context (the user's addition)
- Digests are recorded in the Dockerfile and `compose.yaml`, and updated through Dependabot
  (`docker` ecosystem) under the 7-day cooldown (U1 NFR-WC-15)

## 3. Configuration and Secrets (Q5 A; M1-TECH-06)

**`tenancy.yaml`** (committed; validated at start-up against a JSON Schema with Ajv, refusing
to start on any error, BR-CFG-08):

```yaml
organization: o1
secondFactorRequired: false
projects:
  - id: p1
    environments:
      - id: e
        firstAdmin: h@example.com
      - id: e2
        firstAdmin: h@example.com
```

It holds **no secret**. Secrets are referenced by name in the organization-level settings and
read from `/run/secrets/{name}`.

**Secret files** (each mounted read-only, mode 0400, into only the containers that need it):

| Secret | Used by | Generated by `stack:init` as |
|---|---|---|
| `org-enrollment-{n}` | `org-gateway` | `soorma_em_` + 256 random bits (Base64url), one per first Admin identifier |
| `org-signing-key` | `org-gateway` | An Ed25519 private key (PEM). Its public half becomes the first verify key |
| `org-seed-key` | `org-gateway` | 256 random bits, with a key id |
| `org-counter-secret` | `org-gateway` | 256 random bits |
| `org-log-pseudonym-key` | `org-gateway` | 256 random bits; **separate from the counter secret** (NFR-OI-22, amended) |
| `org-db-app-password` | `org-gateway`, `org-db` | 256 random bits |
| `org-db-migrator-password` | `org-migrate`, `org-db` (**never `org-gateway`**) | 256 random bits |
| `org-db-superuser-password` | `org-db` only | 256 random bits |
| `org-gateway-tls`, `org-db-tls` | each its own service | Key and certificate from the local CA |
| `stack-ca-cert` | every client container | The CA certificate (public) |

**`pnpm stack:init`**:
- writes every file into `deploy/local/.secrets/` with mode 0600, and **refuses to overwrite
  an existing secret**
- writes each first Admin's enrollment material to its secret file **and** to a one-time
  **handover file**, `deploy/local/.secrets/handover/first-admin-{n}.txt`. It prints that
  file's path, never the material. The human reads it, uses it at first authentication, and
  deletes it. Once used, the material can never verify again (BR-FA-03), so a leftover file
  holds nothing usable
- names files by an index `{n}`, never by the principal identifier, which can contain
  characters unsafe in a file name. The mapping from `{n}` to the identifier is in
  `tenancy.yaml`'s order
- runs on the host with Node 26 (type stripping, no decorators) and the OpenSSL CLI, a
  documented prerequisite

**Secrets never pass through environment variables.** A setting that is not secret (a port,
a budget) may.

**Delivery into the containers** (*amended at Code Generation, Q-CG-4 B, the user's answer,
2026-11-09*). On Linux, a Compose `file:` secret is a read-only bind mount that keeps the host
file's owner and mode, so a non-root container cannot read a 0600 file; and Compose refuses
`environment:` secrets in a read-only service (both probed on GitHub's ubuntu-24.04 runner,
Compose v2.38.2). So:
- **One secrets volume per level**: `org-secrets` for the organization level; each environment
  that U4 adds gets `{env}-secrets`
- **One one-shot init container per level**, `org-secrets-init`: it mounts **only this level's**
  `file:` secrets, and copies each into a subdirectory per consuming service with that service's
  owner and mode 0400 (directories 0500): `org-db/` (999), `org-migrate/` (65532),
  `org-gateway/` (65532). The services start only after it completes successfully
- **Each service mounts only its own subpath** of its own level's volume, read-only, at
  `/run/secrets`. An environment's containers never mount `org-secrets`, so organization-level
  secrets never reach them by construction (ID §6)
- **The copies sit in Docker's volume storage**, on the same host as `.secrets/`, and are removed
  by `pnpm stack:down -v`
- **Minimum versions**: `pnpm stack:up` refuses to start, with a message, without Docker Engine
  26 (volume subpaths, API 1.45) and Docker Compose 2.26.0 (the first release that passes a
  subpath to the Engine)

## 4. TLS and the Local CA (Q3 A, the user's change)

| Item | Design |
|---|---|
| **CA** | ECDSA P-256, created by `stack:init`. `basicConstraints` CA, `pathlen:0`; `keyUsage` `keyCertSign`, `cRLSign`; valid 1 year |
| **Name constraints** (critical) | Permitted: DNS `localhost`, DNS `soorma.internal` (that domain and its subdomains), IP `127.0.0.1/32`, IP `::1/128`. **Nothing else.** A leaked CA key cannot issue a certificate any client honouring the constraint will accept for any other name |
| **CA private key** | Kept in `deploy/local/.secrets/` (0600), so U4 to U7 issue their own service certificates without re-creating the CA (the user's change). Never mounted into a container |
| **Service names** | Every service is reached by a name under `soorma.internal` (Compose network aliases): `org-gateway.soorma.internal`, `org-db.soorma.internal`. U4 to U7 follow the scheme (shared-infrastructure.md) |
| **Leaf certificates** | ECDSA P-256, `extendedKeyUsage` `serverAuth`, SANs for the service name (and `localhost` for the published edge port); valid 90 days; reissued by `pnpm stack:certs` |
| **S1** | TLS 1.3 on the edge and internal listeners. The health listener is loopback-only inside the container, plain HTTP, and serves no data |
| **PostgreSQL** | `ssl = on`, TLS 1.3 minimum; `pg_hba.conf` has **only `hostssl` lines**, with `scram-sha-256`. Clients connect with `sslmode=verify-full` and the CA certificate |
| **Callers** | Documented to pass the CA certificate explicitly: `curl --cacert deploy/local/.secrets/stack-ca.pem …`. **Never install the CA in the system trust store** (the user's change) |

## 5. The Org Store (D-ID-OI-01, 02)

- `postgres:18.x`, pinned by digest; named volume `org-db-data`; **no port published to the
  host**
- **Roles**, created at first start by an init script that reads the password files:
  - `soorma_org_migrator` owns the schema and runs the migrations
  - `soorma_org_app` holds only what S1 uses: `SELECT`, `INSERT`, `UPDATE` on its tables;
    **`DELETE` only on `failed_attempts`, `sign_ins`, and `pending_second_factors`**. **No
    `DELETE` on `principals` or `materials`**, so the database enforces "never pruned" too
    (BR-HP-03). No DDL
  - the superuser password is used only by the database container's own initialisation
- **`org-migrate` runs before S1**, as the migrator, under the advisory lock (NFR-OI-18, as
  amended). **S1 never holds the migrator password**, and starts only after `org-migrate`
  has completed successfully (the user's change)
- `synchronous_commit = on` (the default, asserted at start-up)

## 6. Networks and Ports (D-ID-OI-03; the U4 obligation)

| Network | Members | Purpose |
|---|---|---|
| `org` | `org-gateway`, `org-migrate`, `org-db` | The store |
| `org-internal-{env}`, **one per environment** | `org-gateway`, and that environment's `control-gateway` (U4) | The internal interface. **Environments share no network** (the user's U4 obligation) |

| Listener | Container port | Published |
|---|---|---|
| S1 edge (TLS) | 8443 | **`127.0.0.1:8441` on the host only** |
| S1 internal (TLS; signed requests, P-06) | 9443 | **Nowhere**; reachable only on the `org-internal-{env}` networks |
| S1 health (plain, no data) | 8080, bound to `127.0.0.1` in the container | Nowhere; **on no network** (the user's change) |
| PostgreSQL (TLS) | 5432 | Nowhere |

Nothing listens on the host's `0.0.0.0`. Reaching the internal port still requires a signed
request from a configured environment (P-06; I3): network placement is never the check.

## 7. Container Hardening (D-ID-OI-04)

Every U2 container: a non-root user; `read_only: true`, with a small `tmpfs` at `/tmp`;
`cap_drop: [ALL]`; `security_opt: [no-new-privileges:true]`; `org-gateway` with a memory
limit of **768 MiB** (the default hashing budget of 512 MiB plus 256 MiB, P-09); a restart
policy of `unless-stopped` for S1 and `no` for `org-migrate`.

**The one exception** (*amended at Code Generation, Q-CG-4 B, the user's answer*):
`org-secrets-init` runs as **root**, with `cap_drop: [ALL]` plus **only `CHOWN`,
`DAC_OVERRIDE`, and `FOWNER`** (to read the host's 0600 files and set each copy's owner and
mode), **no network** (`network_mode: none`), a **read-only root**, and no-new-privileges.
It **exits** once the copies are made (restart policy `no`). Every long-running container keeps
everything above.

## 8. CI (D-ID-OI-06, 07; the user's addition)

| Step | What |
|---|---|
| Package tests | Against a **PostgreSQL 18 service container**, pinned by digest, with throwaway passwords |
| Image build | Builds the S1 image from `services/org-gateway/Dockerfile` |
| **Image secret check** | Exports the built image's filesystem and runs the D-ID-OI-07 secret-pattern check over it (`soorma_em_`, `soorma_si_`, PEM private keys). Fails on a match |
| Repository secret check | The same patterns over `deploy/` and the working tree |
| Stack smoke test | `stack:init` with throwaway secrets, `docker compose up`, and one first authentication and sign-in over TLS with `verify-full`, then `down -v` |
| `.gitattributes` | The derived breached-list file is marked `binary` (NFR Requirements §4) |

Every new image and action is pinned by digest or SHA (U1 NFR-WC-20).

### Resolved Finding: SECURITY-03 (the user's decision, 2026-11-08)

The finding raised at this stage, and its resolution:
- **Centralized log service**: SECURITY-03 requires log output directed to a centralized log
  service, and the local stack has none. It was marked compliant at NFR Requirements without
  checking that clause. **Resolved by the user's decision: not applicable in M1**, on the
  same grounds as SECURITY-14 and SECURITY-01 at rest. M1 is a local stack with no hosted
  deployment, and a local collector would prove nothing about the hosted service. **Carried
  to Build and Test and to the first hosted deployment**, with NFR-OI-24's obligations
- **PII in logs** (SECURITY-03's fourth clause), raised by the user at the same time: human
  identifiers are typically email addresses (BR-ID-05), and grouping `auth.failed` per
  principal would have put them in logs, including identifiers an attacker submits. **Fixed**:
  logs carry a **keyed pseudonym** instead (HMAC-SHA-256 under a dedicated log-pseudonym key,
  `org-log-pseudonym-key`); alert rules group by it; database records keep the identifier
  (NFR-OI-22 and 23, amended)
