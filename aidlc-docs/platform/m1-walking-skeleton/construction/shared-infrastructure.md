# Shared Infrastructure: soorma-core M1 Local Stack

**Established by**: U2 `org-identity` Infrastructure Design (2026-11-08). See
`construction/org-identity/infrastructure-design/`
**Applies to**: U4 to U7, each adding its deployables to the same local stack (M1-NFR-05)
**Extended by**: U4 `env-human-access` Infrastructure Design (2026-11-11), the first environment level. See
`construction/env-human-access/infrastructure-design/`

Every later unit follows these rules unless its own Infrastructure Design records a reason
to differ.

| Area | Rule |
|---|---|
| **Runtime** | Docker Compose, `deploy/local/compose.yaml`; `pnpm stack:up`, `pnpm stack:down`. A container per deployable. *Settled at U4 Infrastructure Design (Q1 A)*: **one `compose.yaml`; each environment's services, volumes, networks, and secrets are written out in full**, with YAML anchors for the shared shape only (hardening, a service body, the database command). Every service name, volume subpath, network, and secret name is literal, and a Compose-model test (`deploy/test/`) reads `docker compose config` to check what each container mounts |
| **Images** | Two stages: `node:26.13.0` to build, `gcr.io/distroless/nodejs26-debian13:nonroot` to run; **both pinned by digest**. `.dockerignore` excludes `deploy/local/.secrets/`, `.git`, and `node_modules`; Dockerfiles copy explicit paths only. Healthchecks use a Node script (no shell) |
| **Hardening** | Non-root; read-only root with `tmpfs` `/tmp`; every capability dropped; `no-new-privileges`; a memory limit |
| **Health** | A loopback-only health listener inside the container, on no network, returning no detail. **No unauthenticated endpoint on any other listener** |
| **Names** | Every service is reached as `{service}.soorma.internal` (environment services as `{service}.{env}.soorma.internal`), so the local CA's name constraints cover it |
| **TLS** | TLS 1.3 on every listener and database connection. Certificates from the local CA (ECDSA P-256, 90 days, `serverAuth`), issued by `pnpm stack:certs` with the CA key in `deploy/local/.secrets/`. Database clients use `sslmode=verify-full`. Callers use `--cacert`, never the system trust store |
| **Configuration** | `deploy/local/config/tenancy.yaml` (committed, no secrets) is the one tenancy tree. Each deployable reads its own part and validates it against a JSON Schema at start-up, refusing to start on any error. **Organization-level secrets never reach an environment's containers** (ID §6). *Settled at U4 Infrastructure Design (P-06)*: each environment entry carries **one part per environment service** (`controlGateway` at U4; U6 and U7 add theirs). A service reads only its own environment's part. Secrets are named, never held |
| **Secrets** | One file per secret in `deploy/local/.secrets/` (git-ignored, 0600). **Never in environment variables.** `pnpm stack:init` generates them and never overwrites one; each unit adds its own to it. *Amended at U2's Code Generation (Q-CG-4 B, the user's answer, 2026-11-09)*: Compose `file:` secrets are bind mounts that keep the host file's owner and mode, so on Linux a non-root container cannot read a 0600 file; Compose refuses `environment:` secrets in a read-only service. So **each level has one secrets volume and its own one-shot init container**: the organization level `org-secrets` and `org-secrets-init`; each environment U4 adds, `{env}-secrets` and `{env}-secrets-init`. **A level's init container mounts only that level's `file:` secrets**, and copies each into a subdirectory per consuming service, with that service's owner and mode 0400 (directories 0500). **Each service mounts only its own subpath of its own level's volume, read-only, at `/run/secrets`.** So organization-level secrets never reach an environment's containers by construction (ID §6). The init container is the hardening exception (root; `cap_drop: ALL` plus only `CHOWN`, `DAC_OVERRIDE`, `FOWNER`; no network; read-only root; it exits). **The copies sit in Docker's volume storage, on the same host as `.secrets/`, and are removed by `pnpm stack:down -v`.** `pnpm stack:up` refuses to start without **Docker Engine 26** (volume subpaths) and **Compose 2.26.0** (the first release that passes a subpath to the Engine). *Settled at U4 Infrastructure Design (P-02, P-03; the user's O-4)*: **an environment's secrets are mounted files only, never in an environment variable, a command line, `compose.yaml`, `tenancy.yaml`, an image, or any committed file**. They are named `{env}-…`, listed only on `{env}-secrets-init`, and copied by `deploy/local/secrets-init/env.sh {env}`, whose only argument is the environment id. **The one value that crosses levels** is each environment's derived caller **public** key (`{env}-caller-public-key`), listed only on `org-secrets-init` for `org-gateway`. The Compose-model test asserts that no secret crosses a level otherwise. *Corrected in place at U4 Code Generation (2026-11-11, D-CG-EHA-23, the user's decision)*: **the only environment variables are non-secret**: an environment service learns which part of `tenancy.yaml` is its own from `SOORMA_PROJECT` and `SOORMA_ENVIRONMENT` (S2 also has `SOORMA_HEALTH_PORT`); an environment store's init script reads `SOORMA_ENVIRONMENT` (not `SOORMA_ENV`), beside the PostgreSQL image's `POSTGRES_DB`, `POSTGRES_USER`, and `POSTGRES_PASSWORD_FILE` (a path). U6 and U7 use the same names. The Compose-model test holds every service to that allowlist |
| **Stores** | PostgreSQL 18 (pinned by digest), one per deployment level (U4 decides the environment store at its NFR Requirements). Unpublished; `hostssl` and `scram-sha-256` only; a migrator role used only by a one-shot migrate service, and an app role with least privilege. *Settled at U4 NFR Requirements and Infrastructure Design*: the **environment store is PostgreSQL 18, one instance per environment** (`{env}-db`, `env-db.{env}.soorma.internal`), owned by `packages/env-store`, with **one migration sequence** that U5 and U6 extend. In every instance, the database is `soorma_env` and the roles are `soorma_env_migrator` and `soorma_env_app`: fixed names, because the migrations are shared. Isolation is by instance, password, certificate, and network. **Table and column privileges are granted in the migrations** (`REVOKE ALL … FROM PUBLIC`, then only what the app needs, column-level `UPDATE` where a row changes, no `DELETE` unless a rule requires it), each with a test connected as the app role |
| **Networks** | Nothing on the host's `0.0.0.0`. Edge ports on `127.0.0.1` only. **One `org-internal-{env}` network per environment**, joined only by that environment's `control-gateway` and the organization level. No network spans two environments. *Settled at U4 Infrastructure Design (P-05)*: **network `{env}` per environment** holds that environment's store, migrate service, and environment services. **Only `{env}-control-gateway` joins `org-internal-{env}`**. Loopback edges: S1 `127.0.0.1:8441`, E's S2 `8442`, E2's S2 `8443`; U6 and U7 take `8444` upward and record them here |
| **Internal callers** | *Added at U4 Infrastructure Design (Q2 A, with the user's addition)*: S1's `internalCallers` lists **`publicKeys`** per environment, so a caller key rotates with no outage (add the new key, restart S1; switch the environment, restart it; remove the old key, restart S1). **S1 refuses to start if a key (by `kid`) appears in more than one environment, or twice in one**, or if an environment or a secret name appears twice, so `callerByKid` can never attribute one environment's call to another (I1) |
| **Operations notes** | *Added at U4 Infrastructure Design (Q3 A)*: **each service's README has an `## Operations` section** with its rotations and failure behaviour. S1's signing-key rotation says **"wait at least 5 minutes"** at step 2 (every S2 refreshes the verify keys every 5 minutes), and a docs test checks it. U5 to U7 add theirs to their own service's README |
| **Organization-level outage** | *Added at U4 Infrastructure Design (P-01, P-09)*: **no environment service depends on `org-gateway` to start**. S2 starts without it and fetches its verify keys without blocking. The behaviour with S1 stopped is scripted (`deploy/local/scripts/s1-outage.ts`) and run at Build and Test |
| **CI** | Package tests against a PostgreSQL service container; each image built; the secret-pattern check over the repository **and each built image**; one stack smoke test with throwaway secrets |
| **Logs** | JSON to stdout. **No human principal identifier in any log**: a human is named by a log pseudonym (`hp_` + 128 bits of HMAC-SHA-256 over the reference's RFC 8785 form). **Each level has its own log-pseudonym key**: the organization level has `org-log-pseudonym-key`, and **each environment has its own** (`{env}-log-pseudonym-key`), generated by `pnpm stack:init` and mounted **only into that environment's services**. **An environment unit never uses the organization's key**, so a human's pseudonym differs per environment, and **no key is shared across environments** (ID §6; the user's correction at the Infrastructure Design approval, 2026-11-08). No secret or token in any log. A centralized log service is not applicable in M1 (SECURITY-03, the user's decision) |
| **Monitoring** | Security events are added to the named list, and alert rules to `deploy/monitoring/alerts.yaml`, validated by its schema and test. Nothing evaluates them in M1 (SECURITY-14, the user's decision). *U4 added S2's ten events and five rules (U4 Infrastructure Design §9)* |
| **Carried to the first hosted deployment** | Managed-key encryption at rest (SECURITY-01, the user's decision); a centralized log service, log integrity, and retention (SECURITY-03 and SECURITY-14, the user's decisions); per-source attempt counting; managed certificates; access logging at any fronting gateway |
