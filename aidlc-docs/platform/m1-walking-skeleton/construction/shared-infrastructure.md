# Shared Infrastructure: soorma-core M1 Local Stack

**Established by**: U2 `org-identity` Infrastructure Design (2026-11-08). See
`construction/org-identity/infrastructure-design/`
**Applies to**: U4 to U7, each adding its deployables to the same local stack (M1-NFR-05)

Every later unit follows these rules unless its own Infrastructure Design records a reason
to differ.

| Area | Rule |
|---|---|
| **Runtime** | Docker Compose, `deploy/local/compose.yaml`; `pnpm stack:up`, `pnpm stack:down`. A container per deployable |
| **Images** | Two stages: `node:26.13.0` to build, `gcr.io/distroless/nodejs26-debian13:nonroot` to run; **both pinned by digest**. `.dockerignore` excludes `deploy/local/.secrets/`, `.git`, and `node_modules`; Dockerfiles copy explicit paths only. Healthchecks use a Node script (no shell) |
| **Hardening** | Non-root; read-only root with `tmpfs` `/tmp`; every capability dropped; `no-new-privileges`; a memory limit |
| **Health** | A loopback-only health listener inside the container, on no network, returning no detail. **No unauthenticated endpoint on any other listener** |
| **Names** | Every service is reached as `{service}.soorma.internal` (environment services as `{service}.{env}.soorma.internal`), so the local CA's name constraints cover it |
| **TLS** | TLS 1.3 on every listener and database connection. Certificates from the local CA (ECDSA P-256, 90 days, `serverAuth`), issued by `pnpm stack:certs` with the CA key in `deploy/local/.secrets/`. Database clients use `sslmode=verify-full`. Callers use `--cacert`, never the system trust store |
| **Configuration** | `deploy/local/config/tenancy.yaml` (committed, no secrets) is the one tenancy tree. Each deployable reads its own part and validates it against a JSON Schema at start-up, refusing to start on any error. **Organization-level secrets never reach an environment's containers** (ID §6) |
| **Secrets** | One file per secret in `deploy/local/.secrets/` (git-ignored, 0600), mounted as Compose secrets (read-only), only into the containers that use them. **Never in environment variables.** `pnpm stack:init` generates them and never overwrites one; each unit adds its own to it |
| **Stores** | PostgreSQL 18 (pinned by digest), one per deployment level (U4 decides the environment store at its NFR Requirements). Unpublished; `hostssl` and `scram-sha-256` only; a migrator role used only by a one-shot migrate service, and an app role with least privilege |
| **Networks** | Nothing on the host's `0.0.0.0`. Edge ports on `127.0.0.1` only. **One `org-internal-{env}` network per environment**, joined only by that environment's `control-gateway` and the organization level. No network spans two environments |
| **CI** | Package tests against a PostgreSQL service container; each image built; the secret-pattern check over the repository **and each built image**; one stack smoke test with throwaway secrets |
| **Logs** | JSON to stdout. **No human principal identifier in any log**: a human is named by a log pseudonym (`hp_` + 128 bits of HMAC-SHA-256 over the reference's RFC 8785 form). **Each level has its own log-pseudonym key**: the organization level has `org-log-pseudonym-key`, and **each environment has its own** (`{env}-log-pseudonym-key`), generated by `pnpm stack:init` and mounted **only into that environment's services**. **An environment unit never uses the organization's key**, so a human's pseudonym differs per environment, and **no key is shared across environments** (ID §6; the user's correction at the Infrastructure Design approval, 2026-11-08). No secret or token in any log. A centralized log service is not applicable in M1 (SECURITY-03, the user's decision) |
| **Monitoring** | Security events are added to the named list, and alert rules to `deploy/monitoring/alerts.yaml`, validated by its schema and test. Nothing evaluates them in M1 (SECURITY-14, the user's decision) |
| **Carried to the first hosted deployment** | Managed-key encryption at rest (SECURITY-01, the user's decision); a centralized log service, log integrity, and retention (SECURITY-03 and SECURITY-14, the user's decisions); per-source attempt counting; managed certificates; access logging at any fronting gateway |
