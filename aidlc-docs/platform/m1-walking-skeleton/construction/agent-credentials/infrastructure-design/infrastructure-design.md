## 4. Secrets: Mounted Files Only

Generated by `pnpm stack:init` into `deploy/local/.secrets/` (0600, never overwritten), listed
**only on `{env}-secrets-init`**, copied by `deploy/local/secrets-init/env.sh {env}`:

| Secret | New | Copied into |
|---|---|---|
| `{env}-data-gateway-tls` | U6 (by `stack:certs`) | `data-gateway/` |
| `{env}-db-data-password` | U6 | `db/`, `data-gateway/` |
| `{env}-agent-signing-key-1` | U6 | `data-gateway/` |
| `{env}-agent-verify-key-1` | U6 (Q1 A) | **not listed or copied until U7** (`event-ingest/`) |

| `{env}-db-migrator-password`, `stack-ca-cert` | U4 | also `restore/` (D-ID-AC-14) |

`env.sh` gains two lines, U4's and U5's lines unchanged except `db/`'s list gaining the data
password:

```sh
# {env}-restore (postgres, 999; D-ID-AC-14): the migrator password and the CA
# only, in its own subdirectory.
copy restore 999 "$env-db-migrator-password" stack-ca-cert

# {env}-data-gateway (distroless nonroot, 65532; D-ID-AC-09): its own role's
# password, never the app or migrator password; the agent ring, never the human one.
copy data-gateway 65532 \
  "$env-data-gateway-tls" stack-ca-cert "$env-db-data-password" \
  "$env-agent-signing-key-1" "$env-bootstrap-counter-secret"
```

**Never** in an environment variable, a command line, `compose.yaml`, `tenancy.yaml`, an image, or
a committed file.

## 5. S3's Database Role (D-ID-AC-07, 08)

**`env-roles.sql`** creates `soorma_env_data` beside the two existing roles, with the same
attributes (`LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOREPLICATION NOBYPASSRLS`), only if
absent; grants it `CONNECT` on the target database and `USAGE` on schema `public` (no `CREATE`). The
existing two roles' lines are unchanged.

**`db/init/10-soorma-env-roles.sh`** reads `{env}-db-data-password` inside psql, as it reads the
other two, and sets the role's password. **`env-pg_hba.conf`**: the two `hostssl` lines list
`soorma_env_migrator,soorma_env_app,soorma_env_data`.

**`0003`'s grants** are NP-AC-06 as corrected (column-level on `attempt_slots`: `INSERT (slot,
entries)`, `UPDATE (entries, consecutive, next_allowed_at)`, `SELECT`, which is exactly what
admission, the slot's state, and settling need).

**Tests**: the role's attributes (U4's helper, called with the new role); the two privilege tests of
NP-AC-06, **the `soorma_env_data` test running P8's actual `statement()` objects and S3's own statements as the role, each succeeding, beside the refusals (the user's addition at approval)**; the stack-level check that S3 connects as `soorma_env_data` and S2 as `soorma_env_app`.
**The test harness** gains the role in its constants and a connection as it, its existing
constants, connections, and `checkEnvRoleAttributes` unchanged: an export added, existing behaviour
unchanged, shown by U4's and U5's tests passing unchanged (class 1).

## 11. Operations Notes (D-ID-AC-17)

`services/data-gateway/README.md` `## Operations`:

| Topic | Note |
|---|---|
| **Agent-key rotation** | (1) `stack:init` writes `{env}-agent-signing-key-{n+1}` and its verify half; add the new key to `verify` (and, from U7, its verify half to S4's `agentVerify`), restart. (2) Make it `signing`, restart S3. (3) **Wait at least 15 minutes** (L: the longest a token signed by the old key can live), then remove the old key from `verify` and `agentVerify`, restart. A docs test checks the phrase |
| The counter secret | Replace the file and restart: the bound's slots re-key, so every agent's window starts empty. It only ever forgets attempts |
| The lockout residual | An outsider who knows an agent's identifier can stop its new instances from starting while an attack lasts and for at most 60 seconds after; running instances renew unaffected (NFR-AC-10) |
| The store down | Both operations `unavailable` (503, `Retry-After: 5`), nothing written (NFR-AC-14) |
| S1 stopped | No effect: S3 has no organization-level dependency (TC-AC-017) |
| B, L, M | Code constants (60 s, 15 min, 24 h), not configuration (NP-AC-01) |
| **Upgrading a local stack to U6** | The store's roles are created at its first start, so a store initialised before U6 has no `soorma_env_data`, and `0003` fails on its first grant. Re-create it once: `pnpm stack:down -v`, `pnpm stack:init`, `pnpm stack:up`. CI always starts fresh |

`copy backup 999 …` line unchanged).
